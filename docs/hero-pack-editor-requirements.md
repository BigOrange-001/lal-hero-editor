# Windows 英雄包可视化编辑器需求记录

记录日期：2026-10-18。

**状态：已实现，编辑器核心验收通过。** 2026-10-18 用户授权开发，同时补充多包合并导出及精致 UI 要求；初版“不开展开发”的说明已由本次授权取代。具体能力边界、发行位置和验证证据见 [实现与验收](hero-pack-editor-implementation.md)，操作见 [使用指南](hero-pack-editor-guide.md)。

## 产品目标

开发一款电脑端使用的 Windows `.exe` 应用，通过可视化图形页面帮助创作者制作英雄包。创作者应能够在程序内完成英雄与技能编辑、选择游戏素材、处理自定义图片、检查数值、预览、校验和导出，尽量不需要手写配置文件。

应用面向当前游戏的英雄包系统，沿用已有的永久身份、版本、内容摘要、依赖、资源引用、冲突及校验规则。规范依据为 [英雄包作者规范](mod-authoring.md)、[Mod 系统设计](mod-system-design.md) 和 [引擎 API Schema](../schemas/mod-engine-api-v1.json)。

## 英雄条目：new 与 replace

新建时提供两种入口：

| 条目 | 创作目的 | 与游戏现有包格式的关系 |
| --- | --- | --- |
| `new` | 创建独立的新英雄。 | 导出当前游戏支持的 `new` 包。 |
| `replace` | 选择现有英雄，替换或补充该英雄的指定数据、技能和表现。 | 对接当前游戏的 `patch` 包；`replace` 是编辑器中的创作入口名称，不另外生成游戏无法识别的第三种包格式。 |

两种入口分别显示必填项目和选填项目。必填要求由现有包规范、条目类型及所选机制决定，界面应清楚标识、提供说明，并定位缺失或错误字段。`replace` 应能读取和预览目标英雄的当前数据，让创作者只填写需要变动的部分，并生成相应的精确目标和原值／摘要契约。

英雄编辑页面应能配置英雄身份、名称、品质、定位、基础战斗数值、成长、技能关联和表现素材等规范允许的数据。具体字段及合法取值沿用游戏规范，不在本记录中另设一套不兼容的数据定义。

## 技能创建与编辑器

提供独立的技能创建／编辑入口，支持给英雄绑定技能，以及在 `replace` 条目中编辑现有技能。技能页面同样区分必填和选填内容。

以可视化条目或节点组织技能逻辑，至少包含：

- 触发条件与条件组合。
- 技能效果、作用目标和范围。
- 战斗数值及结算参数。
- 特效及对应游戏素材。
- 附加效果、状态和其他机制条目。
- 效果之间的关联和结算顺序。

允许拖动调整结算顺序，并清楚展示修改后实际采用的执行顺序。触发条件、主体效果、特效和附加效果都应可增删、编辑及调整关联；需要保持固定顺序或存在依赖的条目，应在界面说明约束并阻止非法组合。

涉及战斗引擎已有代码、效果类型、素材或其他可复用定义的部分，优先通过下拉框等选择控件直接选取游戏内资源，提供可识别的名称、说明和必要预览，减少手工输入内部 ID。

**2026-10-19 用户确认的验收要求：全部游戏已有技能必须直接作为可导入、可编辑、可导出的完整模板。** 整项引用和只读 JSON 查阅不能代替编辑；不能以旧 API 的 16 动作子集作为完成标准。编辑器和游戏端同步增加完整原生机制数据接口，保留动作、条件、目标、分组、成长、专属召唤／分身、复合机制及被动触发。当前 1077 条技能全部覆盖，73 种原生动作、44 类复合机制、324 个复合机制参数，映射清单见 [战斗机制与编辑器覆盖目录](battle-mechanism-editor-catalog.md)。共同算法继续使用已有引擎，不开放外部脚本。

## 战斗数值与平衡性基准

战斗数值配表提供手动输入和滚轮调节，显示取值范围、单位以及与其他字段的关系；非法、缺失或越界数值应直接提示。

英雄面板数值区设置“查看英雄面板平衡性基准”按钮。打开后可以查看 **橙、紫、蓝、绿、白** 五种品质中，不同角色定位的参考卡牌数值，用于与正在编辑的英雄比较。

参考数据应来自游戏当前实际英雄配置，并标明用于比较的品质、定位以及等级／进阶等面板条件，使比较采用可理解的同一口径。提供参考不等于强制把自制英雄修改成固定模板，也不以未经说明的单一分数替代原始面板数据。

## 图片、卡面与预览

素材编辑区允许导入图片并裁剪，预览裁剪结果。图片处理应满足目标素材槽位的尺寸、格式及容量要求，并在导出前提示不符合规范的资源。

允许自动为导入的图片制作带卡面边框的卡牌图案，提供对应的卡面预览。边框与品质等游戏表现应保持一致；原始图、裁剪结果和带框卡面之间的关系需要清楚，方便创作者调整后再次生成。

2026-10-18 补充明确：品质框必须与原版盾形框保持外观一致，单独保存为透明素材，不能用普通彩色矩形边框代替。支持 RGBA 合成、框内裁剪及人物出框的前后遮挡关系；蒙版可视化编辑，并随工程保留可再次编辑的源图和图层。最终游戏资源为合成后的透明 PNG。

至少提供英雄卡面、头像／图标等相关槽位的预览，以及技能中所选特效与素材的必要预览。技能编辑页面应能看清效果、触发条件和结算顺序的组合；如后续提供运行预览，应明确它与正式游戏战斗引擎的对应关系。

## 自动校验与一键导出

完成编辑后，提供自动检查英雄包／补丁包合法性的操作，以及一键导出操作。

校验应复用游戏实际采用的规则，避免编辑器提示合法而游戏拒绝导入。检查范围包括必填字段、类型和范围、条目及资源引用、技能动作和顺序约束、目标与原值契约、依赖、身份及冲突、文件路径、媒体格式、尺寸、配额和内容摘要。

错误应定位回具体英雄、技能、效果节点或素材，说明修改方式。未满足必须条件时阻止导出；导出成功后生成游戏能够直接导入的标准 `.heropack`，自动组织清单、数据和素材并计算必要摘要。`replace` 导出标准 `patch` 包，`new` 导出标准 `new` 包。

## 多包合并导出（新增要求）

允许选择多个 `.heropack`，把其中的英雄、技能、补丁和素材合并成一个新的包，再编辑或直接导出。支持 `new`、`patch` 以及两者混合的合法组合。

合并产生新的包 UUID；合并后英雄是新身份，不自动继承原包在既有存档中的身份。保留来源包名称、作者、UUID、版本及内容摘要；不同来源的本地 ID、变体、技能和素材需要自动加命名空间，精确改写对应引用。内部依赖吸收，外部依赖继续保留并校验版本及摘要，原有渠道默认值应保留到相应英雄／补丁。

同内容重复选择应去重。同一 UUID 的不同版本／不同内容、相同目标同作用域的补丁冲突或无法保留的原值契约，应明确定位并拒绝，不能静默覆盖、跳过或放宽守卫后声称成功。

## 界面视觉（新增要求）

界面要精致、清楚，适合持续编辑。采用统一的深色工作台、清晰的主次按钮和品质色，左侧工程导航、中间分组编辑、右侧实时预览；保留足够留白、字号层级、说明和错误定位，不以大段 JSON 文本框代替主要创作流程。支持高 DPI、滚动编辑和调整窗口大小。

## 开发范围与验收目标

实现围绕完整创作流程组织：新建条目 → 英雄与技能编辑 → 游戏资源选择／图片处理 → 数值基准对照 → 预览 → 自动校验 → 一键导出。

核心验收目标包括：

1. Windows 用户通过 `.exe` 图形界面完成 `new` 和 `replace` 两种创作流程。
2. 各页面清晰区分必填和选填项，错误能定位到具体编辑位置。
3. 技能支持可视化编辑与拖动结算顺序，已有引擎定义及素材可通过选择控件复用。
4. 有现有技能机制覆盖清单，支持范围与尚待适配的缺口清楚可见。
5. 数值支持手动和滚轮编辑，可以查看五种品质、不同定位的面板参考。
6. 导入图片可裁剪、自动生成带卡面边框的图案并预览。
7. 导出前执行与游戏一致的校验，一键生成可由游戏导入的 `new`／`patch` 包。
8. 多个包可合并成具有新身份的合法包；引用和默认值不丢失，冲突明确拒绝。
9. 主编辑界面、技能编排、裁剪预览和基准对照具有统一、精致的视觉样式。

本轮采用 Python / PySide6 实现离线 Windows 程序，Pillow 处理图片，沿用当前游戏包校验及配置；不启动或修改玩家游戏存档。最终只进行核心创作／保存／合并／校验／导出和启动验证，不做游戏内实测或遍历所有界面的大量测试。
